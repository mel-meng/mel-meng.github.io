# Calibration Cases — Behavior and Implementation Spec

## Behavior specification

### Purpose
Calibration Cases teaches **reasoning about runoff calibration**, not unrestricted curve matching. Every case combines a target hydrograph with site evidence, confidence levels, limited parameter freedom, and a specific learning objective.

The central loop is:

```text
read context → diagnose mismatch → choose a process → change a parameter → run SWMM → compare → refine
```

### Learning contract
The tool should teach that:

- calibration is constrained by physical evidence;
- volume, peak, timing, and whole-series fit are distinct diagnostics;
- routing parameters should not automatically be used to repair volume errors;
- impervious composition changes fast-response behavior;
- infiltration/storage affect losses;
- several parameter combinations may produce similar hydrographs;
- a strong fit metric does not prove the conceptual model is physically defensible.

### Initial cases
Version 1 includes four synthetic cases.

#### 1. Routing mismatch
The runoff volume is already broadly reasonable, but peak/timing are wrong. Editable parameters emphasize Width and roughness. The lesson is to investigate routing before changing loss/composition parameters.

#### 2. Impervious composition
A commercial parcel has aerial/field evidence about impervious cover and direct connection. Editable parameters emphasize `%Impervious`, `%Zero-Impervious`, and a constrained Width. The lesson connects directly to Subcatchment Anatomy.

#### 3. Loss mismatch
A partly pervious basin has the wrong runoff volume. Editable parameters emphasize Green-Ampt conductivity and pervious depression storage. The lesson is to investigate loss processes when volume is wrong.

#### 4. Ambiguous fit
Several parameter combinations can make a strong hydrograph match. Evidence ranges are deliberately important. The case can show **fit passed / evidence failed** to demonstrate non-uniqueness.

### Case content
Each case defines:

- short backstory;
- task statement;
- fixed/known information;
- reasonably known information;
- uncertain information;
- editable parameters and ranges;
- evidence constraints;
- baseline model;
- hidden synthetic target model;
- fit thresholds;
- progressive hints.

### Parameter freedom
Only parameters relevant to a case are editable. Fixed parameters remain visible in the case context but do not appear as sliders.

### Primary visualization
The main chart displays:

- target hydrograph — strong neutral/dark line;
- current model — strong accent line;
- previous model — muted dashed line after an interaction.

Rainfall is fixed by the case and may remain visually secondary.

### Diagnostics
Show separate diagnostics for:

- runoff volume error;
- peak-flow error;
- peak timing error;
- NSE.

Do not replace these with a single “score.”

### Evidence check
Fit and evidence are evaluated independently:

```text
Hydrograph fit        pass/fail
Evidence constraints  pass/fail
Case complete         fit && evidence
```

A case must never be marked complete because of fit alone.

### Previous/current behavior
When a new parameter interaction begins, the last valid current result becomes Previous. Continuous movement of the same slider keeps that previous snapshot until interaction ends.

### Hints
Hints progress from diagnosis to process family to candidate parameter. They should not reveal an exact target parameter value unless the final explanation is explicitly requested.

### Reset
Reset restores exactly:

- baseline parameters;
- baseline hydrograph;
- baseline diagnostics;
- hidden hints/explanation;
- no previous comparison.

### Target design
Targets are synthetic and generated by the same SWMM engine from hidden target parameter sets. This keeps the mechanism internally consistent and reproducible.

### Non-goals
Version 1 is not an optimizer, generic INP editor, professional calibration package, uncertainty analysis system, or leaderboard game.

### Acceptance criteria
- Four cases have distinct stories and learning objectives.
- Every case exposes only its intended parameters.
- Target/current/previous hydrographs are distinguishable.
- Volume, peak, timing, and NSE are reported separately.
- Evidence constraints are evaluated separately from fit.
- A numerically good but evidence-inconsistent result cannot complete a case.
- Reset is deterministic.
- All case baseline and target models run in the existing SWMM WASM runtime.

## Implementation specification

### Files

```text
tools/calibration-cases/
  index.html
  SPEC.md
  cases.js
  model.js
  metrics.js
  constraints.js
  tool.js
  tool.css
```

The app uses existing shared runtime files without modification.

### Responsibility boundaries

#### `cases.js`
Declarative scenario content and parameter bounds. It contains no DOM/rendering code and makes no SWMM calls.

#### `model.js`
Pure INP construction from a complete parameter object. It does not know target/current state, hints, success criteria, or UI.

#### `metrics.js`
Pure hydrograph diagnostics: volume, peak, peak time, errors, NSE.

#### `constraints.js`
Pure evaluation of evidence ranges and fit thresholds. Fit and evidence return independent statuses.

#### `tool.js`
Application state, case switching, interaction snapshots, SWMM calls, chart rendering, hints, reset, and status presentation.

### Case data shape
A case should be data-driven:

```js
{
  id,
  title,
  story,
  task,
  confidence: { known, reasonable, uncertain },
  baseline,
  target,
  editable: {
    parameterName: { label, min, max, step, unit, evidenceRange? }
  },
  thresholds,
  hints
}
```

Avoid custom per-case imperative UI code when declarative data is sufficient.

### SWMM model
Use one subcatchment `S1`, fixed synthetic event rainfall, Green-Ampt infiltration, and one outfall. The parameter object supports:

- area;
- `%Impervious`;
- `%Zero-Impervious`;
- Width;
- slope;
- impervious/pervious roughness;
- impervious/pervious depression storage;
- Green-Ampt suction, conductivity, and initial deficit.

### Output request
Version 1 needs only subcatchment runoff:

```js
[{ key: 'runoff', objectType: 'subcatchment', objectId: 'S1', variable: 'runoff' }]
```

Do not add case-specific logic to the worker/parser.

### Target generation
On case load:

1. run the hidden target parameter set;
2. cache its output for the active case;
3. run the baseline/current parameter set;
4. enable controls.

Case switching must guard against stale async results.

### Simulation scheduling
Use the existing shared client latest-wins behavior. A stale run must never repaint the UI.

### Success evaluation
Keep two explicit results:

```js
{
  fitPassed,
  evidencePassed,
  complete: fitPassed && evidencePassed
}
```

### Testing
Additive tests should verify:

- case IDs and definitions are valid;
- editable bounds contain baseline values;
- evidence ranges are valid;
- model builder maps parameters into INP correctly;
- metric functions on known arrays;
- evidence and fit remain independent;
- every case baseline and hidden target model completes through real vendored SWMM.
